## 1. 先理解程序怎样运行

一个基础程序通常完成：接收输入 → 处理数据 → 输出或保存结果。AI 应用在这个过程中增加对模型服务的调用，文件、函数、异常和 HTTP 都是围绕这条数据流工作的。

| 名称 | 作用 | 本项目中的例子 |
| --- | --- | --- |
| Python | 解释执行 Python 代码的语言与运行环境 | 统计学习分钟数 |
| 函数 | 把一个操作包装成可调用单元 | 统计、保存、检索 |
| 文件 | 让数据在程序退出后仍存在 | 笔记与学习记录 |
| 异常 | 表达执行过程中无法正常完成的情况 | 文件损坏、请求超时 |
| 虚拟环境 | 为项目隔离解释器环境和软件包 | `.venv` |

| HTTP | 客户端和服务端传递请求与响应的协议 | 调用模型 API |

## 2. Python 必备语法

### 2.1 变量与基本类型

变量名绑定到对象，不需要先声明类型。`=` 是赋值，`==` 是相等比较；字符串加引号。

```python
topic = "AI 应用"       # str：文本
minutes = 30            # int：整数
hours = minutes / 60    # float：小数
finished = True         # bool：布尔值
answer = None           # None：暂时没有值
print(f"今天学习 {topic}，共 {minutes} 分钟")
```

`input()` 返回字符串，数字输入要转换：

```python
text = input("今天学了多少分钟？")
minutes = int(text)  # 输入 abc 或空字符串会触发 ValueError
```

先用固定数字练习，理解第五节异常处理后再接收用户输入。

### 2.2 常用容器

| 类型 | 什么时候用 | 示例 |
| --- | --- | --- |
| `list` | 有顺序、需要增删的多条记录 | `[30, 45, 60]` |
| `dict` | 用字段名组织一条信息 | `{"topic": "Python", "minutes": 30}` |
| `tuple` | 一组通常不修改的值 | `(2026, 10, 29)` |
| `set` | 去重或判断是否存在 | `{"Python", "HTTP"}` |

```python
records = [30, 45]
records.append(60)
print(records[0])       # 30，索引从 0 开始
print(records[-1])      # 60，最后一项
print(sum(records))    # 135
print(len(records))    # 3

note = {"topic": "Python", "minutes": 30}
print(note["topic"])
print(note.get("level", "入门"))  # 字段不存在时返回默认值
note["minutes"] = 45
```

空列表和空字典在条件判断中为假。字典按键取值；集合没有列表式的位置索引。

### 2.3 条件与循环

Python 使用缩进表示代码层级，通常每级四个空格。`if`、`for`、`def` 等语句后面有冒号。

```python
minutes = [30, 0, 60]
for day, value in enumerate(minutes, start=1):
    if value >= 45:
        print(f"第 {day} 天：充分学习")
    elif value > 0:
        print(f"第 {day} 天：完成练习")
    else:
        print(f"第 {day} 天：休息")
```

常用运算：`+ - * /`、整除 `//`、余数 `%`、比较 `>= <= !=`、逻辑 `and or not`、成员判断 `in`。`range(3)` 产生 0、1、2，不包含 3。

#### 2.3.1 读懂 `for day, value in enumerate(minutes, start=1):`

这行是 Python 语法：依次取出学习时长，同时给每一项编号，编号从 1 开始。

```python
minutes = [30, 45, 60]

for day, value in enumerate(minutes, start=1):
    print(f"第 {day} 天：学习 {value} 分钟")
```

输出：

```text
第 1 天：学习 30 分钟
第 2 天：学习 45 分钟
第 3 天：学习 60 分钟
```

`for` 的基本结构是 `for 变量 in 可迭代对象:`，下一行缩进写循环体。“可迭代对象”是能够逐项提供数据的对象，例如列表、字符串和 `range()` 的结果。

| 代码片段 | 含义 |
| --- | --- |
| `for` | 开始循环 |
| `day, value` | 两个变量，分别接收本次提供的编号和值 |
| `in` | 从后面的对象中逐项取数据 |
| `enumerate(minutes, start=1)` | 为列表中的值配上从 1 开始的编号 |
| `:` | 表示下面开始循环体 |
| 缩进的 `print(...)` | 每次循环都执行的操作 |

**`minutes` 是数组吗？** 这里的准确名称是列表（`list`），是一种有顺序的数据容器，可以先类比为数组。`minutes` 只是变量名；`[30, 45, 60]` 才是列表对象。

**`start=1` 是赋值吗？** 要区分它所处的位置：

- 单独写 `start = 1` 是赋值语句，把值 `1` 绑定到变量 `start`。
- 在 `enumerate(minutes, start=1)` 的调用括号里，`start=1` 是关键字参数：按参数名把 `1` 传给 `enumerate`，不会因此在调用处创建一个叫 `start` 的变量。

`enumerate` 的调用形式是 `enumerate(iterable, start=0)`：第一个参数是要遍历的对象，第二个参数是编号起点，省略时默认从 0 开始。

```python
minutes = [30, 45, 60]
print(list(enumerate(minutes, start=1)))
# [(1, 30), (2, 45), (3, 60)]
```

这里用 `list(...)` 收集结果，方便观察。`enumerate` 本身是迭代器，遍历时逐次提供一对数据，不会预先生成整个列表。

**`day` 为什么会增长？** `enumerate` 负责每次提供递增的编号，`for` 每次将新的一对数据分别赋给 `day` 和 `value`，这叫“解包”：

| 循环次数 | 本次提供的二元组 | 解包后的结果 |
| --- | --- | --- |
| 第一次 | `(1, 30)` | `day = 1`，`value = 30` |
| 第二次 | `(2, 45)` | `day = 2`，`value = 45` |
| 第三次 | `(3, 60)` | `day = 3`，`value = 60` |

单次解包也可以独立写：

```python
day, value = (1, 30)
print(day)    # 1
print(value)  # 30
```

所以不需要在循环体里写 `day += 1`。若手动管理编号，为本例实现相同输出的写法是：

```python
minutes = [30, 45, 60]
day = 1

for value in minutes:
    print(f"第 {day} 天：学习 {value} 分钟")
    day = day + 1
```

两种写法在循环结束后的 `day` 值不同：本例 `enumerate` 写法留下最后一次编号 `3`，手动写法会再加一次，留下 `4`。比较时应区分“输出相同”与“所有变量状态完全相同”。

**编号和列表索引是两回事。** `start=1` 只影响给出的编号，不改变列表索引，也不会跳过第一个元素；`minutes[0]` 仍是 `30`。`day`、`value` 可以改成其他变量名，例如 `number`、`duration`，含义由各自接收到的数据决定。

动手检查：把 `start=1` 改成 `start=5`，先预测输出，再运行。编号会是 5、6、7，学习时长仍是 30、45、60。

#### 2.3.2 业务场景：知识库问答的参考资料编号

用户问“这个产品如何退款”，检索系统返回两份相关资料。此时列表存多条检索结果，字典存每条的来源与内容，`enumerate` 为本次回答生成方便阅读的编号。

```python
chunks = [
    {"document_id": "policy-2026", "title": "退款规则", "text": "退款条件以购买时适用的规则为准。"},
    {"document_id": "guide-008", "title": "申请流程", "text": "提交订单号并选择售后原因。"},
]

for number, chunk in enumerate(chunks, start=1):
    print(f"[{number}] {chunk['title']}：{chunk['text']}")
```

输出：

```text
[1] 退款规则：退款条件以购买时适用的规则为准。
[2] 申请流程：提交订单号并选择售后原因。
```

这里的规则内容只是虚构教学数据。实际应用中，还应检查产品、版本、用户是否有权访问该资料，再让模型基于证据生成回答。显示引用编号也不代表回答已得到证据支持，需要核对引用和结论。

**容易混淆的业务细节：编号不是文档身份。** 下次检索排序改变时，同一份资料可能从 `[1]` 变为 `[2]`；删除或更新文档要用稳定的 `document_id`，不能用本次显示的编号。需要精确回溯时，还应记录资料版本和片段位置。

| 其他可能场景 | `enumerate` 的用途 | 需要额外考虑 |
| --- | --- | --- |
| 批量导入 100 份手册 | 显示“正在处理第 8/100 份” | 并发任务的编号表示原始顺序，不一定是完成顺序；空批次单独处理 |
| 导出客服回复草稿 | 为导出结果添加序号 | 同时保留真实工单 ID，避免把显示顺序当成工单编号 |
| 展示模型返回的候选方案 | 给每个方案编号供用户选择 | 用户提交选择后，用本次候选集核对编号，避免候选列表变化导致选错 |

### 2.4 三个常见误区

- `a = b` 不会复制列表：两个名称可能指向同一个列表。浅复制可以用 `b.copy()`，嵌套结构需要另外考虑。
- `print()` 显示信息；如果函数要把结果交给别处使用，需要 `return`。
- `"30" + "5"` 得到 `"305"`；`30 + 5` 得到 `35`，先确认类型。

## 3. 函数与模块

### 3.1 参数是输入，return 是输出

```python
def minutes_to_hours(minutes: int) -> float:
    """将非负分钟数转换为小时。"""
    if minutes < 0:
        raise ValueError("分钟数不能为负数")
    return round(minutes / 60, 2)

hours = minutes_to_hours(90)
print(hours)  # 1.5
```

`int` 和 `float` 是类型提示，便于阅读和工具检查；Python 不会仅因写了类型提示就自动验证参数类型。`raise` 主动报告错误。

### 3.2 默认参数与关键字参数

```python
def reached_target(total, target=180):
    return total >= target

print(reached_target(200))             # True
print(reached_target(200, target=300)) # False
```

不要用可变对象作为要累积修改的默认值，例如 `def add(item, items=[])` 会让多次调用共享同一个列表。可改为 `items=None`，在函数内部新建列表。

### 3.3 模块与程序入口

一个 `.py` 文件就是一个模块。`import json` 导入标准库；`from pathlib import Path` 从模块中导入指定名称。自己的文件不要命名为 `json.py` 或 `http.py`，以免遮住标准库。

```python
def main():
    print("开始学习")

if __name__ == "__main__":
    main()
```

直接运行文件时执行 `main()`；被其他模块导入时只提供函数，不自动开始交互或写文件。

设计函数时先写清“接收什么、返回什么、何时失败”。计算逻辑尽量与 `input()`、文件写入和网络请求分开，便于检查和复用。

### 3.4 业务场景：把客服工单规则拆成可复用函数

假设客服机器人要处理来自网页、邮件和后台的咨询。这些入口都需要校验工单字段，适合复用一个函数：

```python
def validate_ticket(ticket: dict) -> dict:
    ticket_id = ticket.get("ticket_id")
    question = ticket.get("question")
    if not isinstance(ticket_id, str) or not ticket_id.strip():
        raise ValueError("缺少有效的工单 ID")
    if not isinstance(question, str) or not question.strip():
        raise ValueError("咨询内容不能为空")
    return {"ticket_id": ticket_id.strip(), "question": question.strip()}

ticket = validate_ticket({"ticket_id": "T-1001", "question": " 如何查看使用教程？ "})
print(ticket)
```

输入是工单字典，输出是清理过的必要字段。缺少咨询内容时抛出 `ValueError`，调用者可以提示用户补充；正常返回后，后续步骤才进行知识检索或模型调用。

这段代码只处理字段校验。真实业务还需要根据登录用户检查其是否有权访问该工单，不能只凭传入的 ID 决定权限。

| 可拆成函数的业务步骤 | 输入 → 输出 | 为什么拆开 |
| --- | --- | --- |
| 清理文档文本 | 原始文本 → 规范化文本 | 导入和重新建索引时可复用 |
| 检索相关资料 | 问题及已授权资料范围 → 相关片段 | 可独立检查“是否检索到证据” |
| 计算调用费用 | 用量、实际价格 → 费用明细 | 与模型请求分离，便于按账单核对 |
| 校验生成结果 | 模型输出 → 有效结果或错误 | 防止缺失字段直接进入后续业务流程 |

函数不是“写得短”就合适。优先让一个函数完成一项清晰职责，并说明它会不会修改数据库、写文件或调用外部接口。

## 4. 文件、路径与 JSON

### 4.1 使用 pathlib 表达路径

```python
from pathlib import Path

folder = Path("data")
folder.mkdir(parents=True, exist_ok=True)
path = folder / "note.txt"
path.write_text("今天学习 Python", encoding="utf-8")
print(path.read_text(encoding="utf-8"))
```

相对路径按当前工作目录解析，不一定是脚本所在目录。`Path(__file__).resolve().parent` 可定位脚本目录；本项目示例用它定位项目根目录，避免从其他目录启动时写错位置。

Windows 绝对路径可写为 `Path(r"D:\Documents\notes")`，避免反斜杠被识别为转义字符。`/` 在 `Path` 之间表示拼接路径。

### 4.2 文件打开模式

| 模式 | 行为 |
| --- | --- |
| `r` | 读取，文件不存在时报错 |
| `w` | 写入，已有文件会截断覆盖 |
| `a` | 追加，不清空已有内容 |
| `x` | 只创建新文件，已存在则报错 |
| `b` | 二进制，例如 `rb`，用于图片等内容 |

```python
with open("study.txt", "a", encoding="utf-8") as file:
    file.write("今天学习 30 分钟\n")
```

`with` 确保正常或异常退出时关闭文件。小型文本可直接用 `read_text()`，大文件更适合逐行读取。写入前要确认路径和覆盖行为。

### 4.3 JSON 与 Python 对象的对应

JSON 是常见的数据交换文本格式。JSON 字符串与字段名用双引号；JSON 中的 `true/false/null` 对应 Python 的 `True/False/None`。

```python
import json
from pathlib import Path

records = [{"topic": "Python", "minutes": 30}]
text = json.dumps(records, ensure_ascii=False, indent=2)
Path("records.json").write_text(text, encoding="utf-8")
loaded = json.loads(Path("records.json").read_text(encoding="utf-8"))
print(loaded[0]["topic"])
```

- `dumps`：Python 对象 → JSON 字符串；`loads`：JSON 字符串 → Python 对象。
- `dump/load`：直接与已打开的文件对象交互。
- `ensure_ascii=False` 使中文易读，`indent=2` 设置缩进。
- 解析成功不代表字段有效，还要检查结构和业务范围，如分钟数不能为负。

文件不存在与文件损坏应区别处理：初次运行没有记录，可以返回空列表；损坏的数据应提示检查，不应当作空记录再覆盖。

### 4.4 业务场景：知识库导入、评估数据与配置

| --- | --- | --- | --- |
| 产品手册导入 | PDF、Markdown 或文本 → 带来源的知识片段 | 保存原始资料，读取解析后的记录 | 扫描 PDF 可能需要 OCR；编码、格式及资料版本不同 |
| 问答效果评估 | 问题、参考证据、评分规则 → 逐题结果 | JSON 保存结构化样本，便于比较版本 | 资料包含私人信息，不能直接提交到公开仓库 |
| 模型结果导出 | 提取字段 → JSON 或 CSV | 让下游程序读取结果 | JSON 语法正确但字段含义或类型错误 |
| 应用配置 | 配置文件或环境变量 → 运行参数 | 区分业务参数、环境地址与认证信息 | 配置不存在、非法值、把密钥误放入版本库 |

例如一条评估记录可以包含 `question_id`、`question`、`expected_source_id` 和 `passed`。它让你回答“修改检索逻辑后，原本通过的哪些问题失败了”。

小练习可以把记录存为本地 JSON。多个进程或多位用户同时修改业务数据时，单文件覆盖写入可能丢失更新，应按需求使用支持事务的数据库等存储；把文件保存成功与整项业务处理成功分开判断。

## 5. 异常与调试

### 5.1 捕获能处理的具体异常

```python
try:
    minutes = int(input("学习分钟数："))
    if minutes < 0:
        raise ValueError("不能为负数")
except ValueError as error:
    print(f"请输入有效的非负整数：{error}")
else:
    print(f"已记录 {minutes} 分钟")
```

`try` 放可能失败的操作；`except` 处理匹配的异常；`else` 在没有异常时运行；`finally` 无论是否异常都用于执行收尾。多个 `except` 要先具体、后一般。

| 异常 | 常见原因 | 应对方式 |
| --- | --- | --- |
| `ValueError` | 字符串无法转数字、数据范围错误 | 提示输入或修正数据 |
| `TypeError` | 类型或参数数量不符合要求 | 检查调用和数据类型 |
| `KeyError` | 访问不存在的字典键 | 检查响应字段，必要时用 `get` |
| `IndexError` | 列表索引越界 | 检查长度和空列表 |
| `FileNotFoundError` | 路径不存在 | 检查工作目录和路径 |
| `PermissionError` | 没有读写权限 | 检查文件占用和保存位置 |
| `json.JSONDecodeError` | 响应或文件不是有效 JSON | 检查原始内容，勿直接当作成功 |
| `ModuleNotFoundError` | 当前解释器找不到包 | 检查虚拟环境和安装位置 |

不要用 `except: pass` 隐藏错误。需要向调用方交代失败时，可继续 `raise`；已捕获但程序应失败退出时，可用 `raise SystemExit(1)`。

### 5.2 读报错的顺序

先看最后一行异常名称与信息，再定位属于自己文件的行号，最后检查该行使用的数据。用最小输入重现，单次只改一个原因。

```python
print(type(value), repr(value))
```

上述语句放在已定义变量 `value` 的代码位置使用，帮助区分空字符串、数字和文本。不要打印 API Key 等敏感值。稳定程序可使用 `logging` 记录阶段、耗时与错误，避免把整份私人资料写入日志。

### 5.3 业务场景：批量导入时明确记录部分失败

假设用户上传了 50 份资料，其中一份编码错误。对于允许部分成功的导入业务，应分别记录成功和失败，而不是静默忽略错误，或仅显示“全部导入成功”。

```python
def parse_document(document: dict) -> str:
    text = document.get("text")
    if not isinstance(text, str) or not text.strip():
        raise ValueError("文档没有可用文本")
    return text.strip()

documents = [
    {"id": "doc-01", "text": "产品安装步骤"},
    {"id": "doc-02", "text": ""},
]
successes = []
failures = []

for document in documents:
    try:
        text = parse_document(document)
    except ValueError as error:
        failures.append({"document_id": document["id"], "reason": str(error)})
    else:
        successes.append({"document_id": document["id"], "text": text})

print(f"成功 {len(successes)} 份，失败 {len(failures)} 份")
print(failures)
```

此例输出成功 1 份、失败 1 份，并能定位到 `doc-02`。它只模拟文本校验，未实现真正的文件解析、数据库写入和断点恢复。

业务应先决定能否部分成功：文档导入常可以按文件分别处理；涉及多个步骤共同成立的数据更新，则需要事务或补偿等机制，不能简单捕获错误后继续当作完成。

| 故障 | 业务响应思路 |
| --- | --- |
| 用户上传无效格式 | 告知具体文件和支持的格式，不进行无意义重试 |
| 外部模型临时不可用 | 在符合服务规则且允许重复调用时限次重试；仍失败则明确提示 |
| 工单写入后响应丢失 | 先用业务标识查询结果，避免再次创建同一工单 |
| 程序出现未预料错误 | 保留可定位的错误信息，让任务失败并进入排查，勿伪装成成功 |

## 7. Git 与 GitHub

### 7.1 四个位置

工作区（你编辑的文件）→ 暂存区（下次提交选中的内容）→ 本地提交历史 → GitHub 远程仓库。

| 命令 | 用途 |
| --- | --- |
| `git status -sb` | 查看分支与改动 |
| `git diff` | 看未暂存的已跟踪文件差异 |
| `git add 路径` | 选择要提交的文件 |
| `git diff --staged` | 检查即将提交的内容 |
| `git commit -m "说明"` | 保存一次本地版本 |
| `git log --oneline -5` | 查看最近提交 |
| `git remote -v` | 查看远程地址 |
| `git fetch origin` | 取得远程历史，不自动合并 |
| `git pull --ff-only` | 在可快进时同步当前跟踪分支 |
| `git push` | 推送本地提交 |

### 7.2 第一次使用

本项目已经有 Git 仓库，无需重复初始化。只有全新目录才需要 `git init`；已有远程仓库通常使用 `git clone 地址` 获取。

提交身份与登录认证是不同概念：`user.name/user.email` 决定提交记录署名；登录凭据决定能否访问和推送仓库。Git 作者邮箱会进入提交历史，公开仓库可以使用 GitHub 提供的隐私邮箱。

```powershell
git config --get user.name
git config --get user.email
git remote -v
git branch --show-current
```

首次添加远程和推送方式见[维护约定](../CONTRIBUTING.md)，请替换占位符并核对实际分支名。

### 7.3 日常修改示例

```powershell
git status -sb
git diff
git add docs/开发基础手册.md CHANGELOG.md
git diff --staged
git commit -m "docs: 补充 HTTP 状态码说明"
git push
```

未跟踪文件不会出现在普通 `git diff` 中，要同时看 `git status`。提交说明写清本次变化。每次提交尽量围绕一个学习主题或一个修复。

### 7.4 分支、冲突与撤销

较大修改可用 `git switch -c codex/主题名称` 创建分支。Pull Request 是让远程评审与合并改动的请求，创建分支本身不会自动创建它。

- 取消暂存但保留工作区修改：已有首个提交后，使用 `git restore --staged 文件路径`。
- 丢弃未提交的文件修改：`git restore 文件路径`。这会丢掉该文件的工作区改动，先确认差异或备份。
- 撤销已经提交的修改：可以用 `git revert 提交编号` 生成一个反向提交，保留历史。
- 合并冲突：打开带有冲突标记的文件，决定最终内容，删除标记，检查运行结果，再按 Git 提示继续。不要只机械删除标记。

避免用强制推送或 `reset --hard` 处理不理解的问题。`.gitignore` 只防止未跟踪文件被加入，不会自动移除已经提交的密钥；泄露的密钥首先应在服务端撤销或更换。

### 7.5 业务场景：追踪提示词和解析规则的变化

| 场景 | Git 中记录什么 | 业务价值与边界 |
| --- | --- | --- |
| 客服提示词增加“必须附来源”规则 | 提示词修改、评估样本、前后结果摘要 | 能知道哪次修改影响了回复；不能只凭提示词文本判断有效 |
| PDF 解析修复 | 解析代码、脱敏的最小问题样例、检查方法 | 新修改能验证旧问题不会复发 |
| 多人同时改检索流程 | 功能分支、Pull Request、评审意见 | 在合并前比较修改，发现冲突 |
| 新版本回答质量下降 | 引入改动的提交及回退修复 | 可恢复代码版本；已写入的数据和外部动作需要另外处理 |

具体流程：保存基线评估 → 修改一个因素 → 运行同一组任务 → 将改动和结果一起提交。Git 提交编号可以与部署版本关联，但 `git push` 本身只上传代码，不表示应用已经部署，也不会自动撤回已发送的邮件、已创建的工单或数据库变化。

## 8. HTTP 与 API

### 8.1 一次请求包含什么

API 是程序之间交互的接口；很多 Web API 通过 HTTP 通信。客户端发送请求，服务器返回响应。

```text
请求：方法 + URL（路径/查询参数）+ Headers + 可选 Body
响应：状态码 + Headers + Body
```

例如：`GET /lesson?topic=Python` 请求课程信息。查询参数用于传递筛选条件；请求头可能声明内容类型和认证；请求体可包含 JSON 数据。

| 方法 | 常见用途 |
| --- | --- |
| GET | 获取资源 |
| POST | 创建资源或提交一次处理请求，如模型生成 |
| PUT | 按接口约定替换资源 |
| PATCH | 按接口约定修改部分字段 |
| DELETE | 删除资源 |

服务接口可能采用不同约定，调用前阅读文档。不要因为方法名字就推断重复发送必然安全，尤其是创建订单、发送消息等操作。

### 8.2 常见状态码

| 状态码 | 含义与处理方向 |
| --- | --- |
| 200 | 请求成功，继续检查响应内容 |
| 201 | 已创建资源 |
| 204 | 成功且无响应体，不应强行解析 JSON |
| 400 | 请求参数有误，检查文档和字段 |
| 401 | 缺少或无效的认证信息 |
| 403 | 服务拒绝执行，检查权限和策略 |
| 404 | 路由或资源不存在 |
| 429 | 超过速率限制，按服务规则退避或等待 |
| 500/502/503 | 服务端或上游故障，视请求性质决定是否重试 |

网络超时不一定有 HTTP 状态码。HTTP 200 也不等于业务任务正确，仍要验证响应字段和最终结果。

### 8.3 用标准库发送请求

下面的 `url` 需要使用实际接口地址，完整离线演示见下一节。

```python
import json
from urllib.request import Request, urlopen

def get_json(url):
    request = Request(url, headers={"Accept": "application/json"}, method="GET")
    with urlopen(request, timeout=5) as response:
        return json.loads(response.read().decode("utf-8"))
```

URL 中含中文查询参数时，用 `urllib.parse.urlencode` 编码，不要直接拼接未转义的用户输入。

发送 JSON 请求体的典型结构如下，路径、字段和认证方式由真实服务文档决定：

```python
payload = {"question": "什么是上下文？"}
body = json.dumps(payload, ensure_ascii=False).encode("utf-8")
request = Request(
    url,
    data=body,
    headers={"Content-Type": "application/json", "Accept": "application/json"},
    method="POST",
)
```

这段只展示如何构造请求，`url` 必须提前赋值，随后还需要调用 `urlopen()` 才会发送。真实模型 API 的字段通常与示意不同。

### 8.4 实际运行与异常顺序

```powershell
python examples/04_http_demo.py
```

该程序启动仅监听本机的临时服务，发送带中文参数的 GET，再请求不存在的路径，最后关闭服务。可观察到包含学习主题的 JSON 和 `HTTP 失败：404`。它不模拟模型推理，也不会调用付费服务。

标准库中的 `HTTPError` 是 `URLError` 的子类，因此先捕获 `HTTPError` 以保留状态码，再处理网络错误。JSON 解码错误、超时与服务错误要分别考虑。

给请求设置超时。后续添加重试时，应限制次数，只重试合适的错误，并确认重复请求不会产生重复副作用。日志记录状态、耗时、请求标识即可，不记录认证头。

### 8.5 业务场景：跨系统请求的结果怎么处理

| 业务场景 | 请求输入 → 期望输出 | 常见失败与业务处理 |
| --- | --- | --- |
| 客服回复草稿生成 | 问题和已授权证据 → 草稿及用量 | 超时或 429：限制重试；检查输出后再展示或进入审核 |
| 查询订单状态 | 已验证用户和订单标识 → 允许查看的状态 | 401/403：处理认证或权限；不能把拒绝访问当成“订单不存在” |
| 创建售后工单 | 用户确认的字段和业务请求标识 → 工单 ID | 响应丢失时，先按业务标识查询；若接口支持，使用幂等键防重复 |
| 接收外部系统通知 | 事件标识和事件内容 → 接收结果 | 按提供方协议验证来源、识别重复事件，再处理；确认收到与处理完成要区分 |
| 启动长时间文档解析 | 文件标识 → 任务 ID，再查询状态 | 仅取得任务 ID 不等于解析成功；明确处理中、失败和完成状态 |

例如调用创建工单接口后发生超时，可能是请求没送到，也可能是服务已创建工单但响应没回来。不能仅凭客户端报错断定“没有创建”，直接重试可能生成重复工单。

幂等键是服务端按协议识别重复业务请求的一种机制，不是任意添加一个请求头就自动生效。只有实际接口文档支持时才能依赖它；查询、重试、事件验证的具体方法也以提供方协议为准。

## 10. 常见问题速查

| 现象 | 优先检查 |
| --- | --- |
| `python` 无法识别 | Python 安装、PATH，尝试 Windows 的 `py` |

| 数字不能相加 | `input()` 的字符串是否转成数字 |
| 运行找不到文件 | `Get-Location` 与脚本路径是否匹配 |
| 中文乱码 | 文件与终端编码；读写文件显式指定 UTF-8 |
| 包安装了仍然无法导入 | `sys.executable` 是否指向安装时的解释器 |
| 激活虚拟环境失败 | 直接调用 `.venv\Scripts\python.exe` |
| Git 不允许提交 | 本仓库是否配置作者姓名和邮箱 |
| push 失败 | 远程地址、认证、权限、分支跟踪关系和远程新提交 |
| GitHub 没有新内容 | 是否只做了 add/commit，尚未 push |
| API 401/403 | 密钥、有效期、接口权限与服务策略 |
| API 429 | 调用频率或配额；遵循服务返回的限流信息 |
| JSON 解析失败 | 实际响应是否 HTML、空内容或错误文本 |
