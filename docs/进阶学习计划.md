# AI 应用进阶学习计划：第 25–60 周

本文件承接[基础学习路线](../AI应用学习路线图.md)。更新时间：2026-10-29。结合《深入理解 AI Agent》和用户提供的学习导图补充设计；周次与项目属于本项目的学习安排，不是原书或导图的课程承诺。

## 1. 范围与进入条件

默认每周 8–10 小时，第 25–48 周约 192–240 小时，第 49–60 周另约 96–120 小时。任务超出当前能力时顺延；较难的训练、前端、并发与部署练习可能需要更多时间。各阶段完成标准比固定日期优先。

进入第 25 周前，应能解释并修改自己的知识库助手，完成一次真实模型调用，有固定评估任务，并能用 Git 提交和推送。尚未达到时继续基础阶段。

第 25–48 周是应用工程主线，第 49–60 周为模型方向选修。先完成应用层基线，再决定是否需要微调；是否租用 GPU、开通付费服务或部署外网系统，在实际实施时按真实预算和授权决定。本计划不启动这些服务。

项目统一使用虚构或已获授权的样本。学习计划中出现“企业”表示模拟相应业务约束，不表示已完成真实企业上线。现有标准库基础示例保持独立；进阶项目增加依赖时，各自记录环境、版本、配置与运行说明。

## 3. 每周任务与业务验收

勾选代表相应成果已经验证，不代表仅看完文档。表中的数量是学习用规模；效果门槛在运行候选方案前，根据业务需求写入验收规则，不在看到结果后临时修改。

### 阶段 A：模型原理与提示工程，第 25–28 周

业务项目：从客服咨询中提取订单号、问题类别和缺失字段，生成回复草稿。

输入：虚构咨询文本和字段定义。输出：结构化字段、缺失项提示、回复草稿。关键边界：不能凭空补订单号或承诺不存在的售后政策。

| 完成 | 周次 | 学习任务 | 交付与验收 |
| --- | --- | --- | --- |
| [ ] | 25 | Token、嵌入、注意力、Transformer、训练与推理的区别 | 画出“文本—Token—模型—输出”的流程，记录长短输入对用量和耗时的影响；模型内部原理与 API 可观测信息分开说明 |
| [ ] | 26 | 角色、任务、规则、示例、输出约束及参数传递 | 设计约 30 条工单样本，比较零示例与少示例提取；缺字段、歧义、无关输入分别计分 |
| [ ] | 27 | 上下文预算、提示注入、外部资料边界、输出校验 | 对不可信资料中夹带的指令建立任务；验证引用、字段类型和越权工具调用；保留成功及失败证据 |
| [ ] | 28 | 选择一个低代码平台体验；回顾直接调用 API 的实现 | 用 Dify 或 Coze 等平台复现同一工单流程，比较字段校验、运行记录、导出与集成方式；选择可继续维护的一种实现 |

原书对应：第 1、2、5、7 章。对推理提示、规划或审核策略的实验，评价最终答案和执行结果；不以生成冗长推理文本作为掌握标准。

### 阶段 B：企业知识库与高级 RAG，第 29–34 周

业务项目：不同角色的员工查询不同范围的产品或公司制度资料。

输入：带版本、来源、更新时间、访问范围的资料，以及已验证的用户身份。输出：有来源、版本和证据位置的答案。关键边界：资料过期、无证据、跨角色访问和检索遗漏。

| 完成 | 周次 | 学习任务 | 交付与验收 |
| --- | --- | --- | --- |
| [ ] | 29 | PDF、表格和扫描文档解析；分块与元数据 | 用至少 3 种版式测试解析，保留原始资料与片段对应关系；OCR 按需要引入，记录无法可靠解析的页面 |
| [ ] | 30 | 向量索引与数据库；相似度、Top-K、持久化 | 选择一个向量存储，完成写入、检索、删除、重启恢复；用小样本比较精确搜索与近似检索，概览 HNSW、IVF/PQ 等取舍 |
| [ ] | 31 | BM25、向量检索、混合召回与重排序 | 用相同问题比较方案；分别统计证据召回和答案质量，专有名词与自然语言问题分开分析 |
| [ ] | 32 | 查询改写、多查询、上下文补充与 Agentic RAG | 从已确认的失败样本选一个策略做对照；说明新增调用数、耗时和费用，避免把更多步骤等同于更好效果 |
| [ ] | 33 | 身份验证、资料授权、增量更新与删除 | 构造两个角色、两个资料版本；检索前根据可信身份限定范围；验证越权查询、旧资料失效和删除后的索引同步 |
| [ ] | 34 | 框架化与回归评估 | 用 LangChain 或 LlamaIndex 中的一套重构必要部分；保留约 50 条评估任务及独立保留集，检查效果、来源、权限和更新链路 |

阶段放行：能区分解析失败、检索失败、生成失败；未授权证据不进入模型上下文；重建索引步骤可复现。框架重构要与原实现比较，不为了更换框架无故重写。

原书对应：第 2、3、7 章。多模态检索、知识图谱等作为解决已发现问题的扩展，不设为所有学习者的前置条件。

### 阶段 C：业务 Agent 与协作，第 35–40 周

业务项目：售后助手查询订单、检索政策、生成工单草稿，经用户确认后执行创建。

输入：问题、已验证用户、业务规则和模拟订单。输出：查询结果或工单草稿、执行状态、真实或模拟工单 ID。关键边界：无权限、参数缺失、用户取消、服务超时、进程重启和重复提交。教学阶段先接模拟业务接口。

| 完成 | 周次 | 学习任务 | 交付与验收 |
| --- | --- | --- | --- |
| [ ] | 35 | Function Calling、工具契约、确定流程与自主循环 | 把查询、规则检索、草稿创建做成工具；在程序侧验证参数和权限；字段缺失时澄清，不能靠模型猜测 |
| [ ] | 36 | LangGraph 的节点、边、状态和条件分支；规划与执行 | 实现“查询—检索—草稿—确认—执行”的状态图；比较确定流程与自由循环的成功率、调用数和可解释性 |
| [ ] | 37 | 检查点、状态持久化、人工介入、幂等和恢复 | 在创建前后模拟中断；恢复后不重复建单；等待确认时可取消，状态包含请求 ID、确认内容与执行结果 |
| [ ] | 38 | MCP 的客户端、服务端、工具与资源；错误和生命周期 | 把只读政策查询封装成最小 MCP 服务，再由客户端调用；检查认证、工具参数、错误响应、超时与退出 |
| [ ] | 39 | 多 Agent 分工、上下文隔离、A2A 的发现与任务状态 | 先比较单 Agent 与“检索—审核”分工；再用两个本机服务演示 A2A 任务提交与结果返回，分别验证身份、超时与失败状态 |
| [ ] | 40 | DeepResearch 小练习与协作收益判断 | 给一个产品调研问题生成检索计划、收集有来源的资料、输出有引用报告；比较单体与分工版本，并写一页 AutoGen／CrewAI 与当前实现的差异笔记 |

阶段放行：故障后能判断任务未开始、处理中、等待确认、已完成或失败；没有确认的写操作不执行；重复请求不会创建重复对象。多 Agent 与 A2A 是不同层面的概念，不把多个角色提示词当成已经完成跨服务协议接入。

原书对应：第 1、2、4、6、7、9、10 章。MCP 接外部能力，A2A 用于 Agent 间交互；具体实现按所选版本的官方协议验证。

### 阶段 D：部署与运维，第 41–44 周

业务项目：把售后助手交付到一个可复现的测试环境，观察负载和故障。

输入：应用代码、配置、测试流量及依赖服务。输出：可访问的服务、运行指标、故障记录、备份恢复和回退证据。

| 完成 | 周次 | 学习任务 | 交付与验收 |
| --- | --- | --- | --- |
| [ ] | 41 | FastAPI、请求校验、认证授权、流式响应或异步任务 | 将已有业务逻辑封装为接口；先沿用 Streamlit，记录前后端接口；验证用户隔离、取消与错误响应 |
| [ ] | 42 | Linux 基础、Docker、持久化卷、环境配置与迁移 | 在干净测试环境按说明启动应用和必要服务，重启后记录仍在；外网发布时补齐 HTTPS、访问限制和密钥配置 |
| [ ] | 43 | 可观测性、限流、队列、缓存、并发及压测 | 串联请求 ID、工具轨迹和错误；记录成功率、P50/P95 延迟、Token 与费用；限流或依赖故障时能降级或明确失败 |
| [ ] | 44 | CI/CD、版本记录、数据库备份、恢复及回退 | 演练部署旧新版本、恢复测试数据和回退；区分回退代码与回退数据；生成一份运行与故障处理手册 |

阶段放行：交付说明包含依赖、启动、健康检查、权限、存储、备份、回退和已知限制。压测只针对获授权环境，先写明并发、请求分布、持续时间与目标，不用几次成功演示代表容量验证。

日志和指标先用最小实现；再根据需要选择 Prometheus/Grafana 等工具。没有足够规模需求时，不把集群或 Kubernetes 设为必修。

### 阶段 E：商业综合项目，第 45–48 周

默认做电商售后 Copilot。使用虚构订单、用户和政策，模拟“查询订单—核对政策—起草方案—人工确认—创建工单”。同一项目持续迭代，比同时开始三个未完成项目更便于检查整体能力。

| 完成 | 周次 | 学习任务 | 交付与验收 |
| --- | --- | --- | --- |
| [ ] | 45 | 需求、业务状态、接口与验收设计 | 写用户故事、输入输出、权限、失败状态和成本约束；冻结一组包含正常与异常任务的验收集 |
| [ ] | 46 | 端到端集成 | 接通知识库、身份、订单、工单、状态图和界面；核心规则由业务代码验证，模型提供提取、选择与草稿能力 |
| [ ] | 47 | 故障与边界验证、性能与效果分析 | 测试越权、重复提交、取消、资料过期、依赖超时和重启；对每个失败给出轨迹、原因和修复或限制 |
| [ ] | 48 | 试用、评估、交付与复盘 | 由试用者完成完整任务；交付代码、演示、架构图、评估报告、部署与恢复说明、费用记录和待解决问题 |

可以替换项目主题，但保留权限、更新、工具、状态恢复、评估和交付这些验收维度：

| 主题 | 输入 → 输出 | 必须体现的业务难点 |
| --- | --- | --- |
| 电商售后 Copilot | 用户诉求和订单 → 售后方案与确认后的工单 | 用户权限、政策版本、重复操作、写入确认 |
| 企业 HR 助手 | 员工身份、制度、岗位信息 → 有来源的政策答复或草稿 | 岗位与角色权限、制度生效时间、个人信息处理；不自动作出招聘决定 |
| DeepResearch | 问题、范围和来源要求 → 可追溯的调研报告 | 来源质量、去重、矛盾证据、不确定性、成本和任务恢复 |

若选择一种主题，其余两种只写迁移设计，不标为已完成。需要独立前端时，再补 HTML/CSS/JavaScript、TypeScript 和框架基础；现有周数不包含从零精通独立前端。

### 阶段 F：模型微调与推理部署，第 49–60 周，选修

业务项目：针对稳定的工单分类和字段提取任务，对比提示词、小规模微调与不同推理部署方案。微调目标是可测量的行为变化，不以训练跑通或训练损失下降代表业务改善。

进入条件：应用层已有评估基线；补齐张量、梯度、损失、训练集/验证集/测试集、过拟合和基础 PyTorch 操作。若这些概念仍不熟，应增加准备时间；资源不合适时缩小模型和序列长度，先做 CPU 可运行的数据与评估练习。

## 4. 统一项目验收材料

每个阶段至少保存以下材料，目录可以随项目结构调整：

- 业务说明：用户、触发条件、输入输出、成功条件和暂不支持的范围。
- 运行说明：依赖与版本、示例配置、数据准备、启动和检查方式。
- 数据说明：来源、权限、版本、训练/验证/测试用途；公开仓库只放可公开样本。
- 评估记录：基线、候选方案、判分规则、逐题结果、失败轨迹及成本。
- 故障记录：发生条件、实际结果、恢复方法、重复执行和人工介入边界。
- 交付说明：部署环境、存储、观测、备份恢复、代码与数据回退、已知限制。

权限隔离、未经确认的写入、重复工单等关键业务要求应使用明确的通过/失败检查；开放回答使用证据与人工复核相结合的方法。小样本实验结果只用于当前学习项目，不外推为所有业务的可靠性保证。

## 6. 如何持续维护这份计划

每完成一周再勾选，并在对应项目记录实际投入、卡点和验收证据。变更框架或模型时更新官方资料与版本，保留旧基线。周计划属于未来工作，未实施的内容不能写进项目“已实现功能”。

每次完成实质内容后，按[维护约定](../CONTRIBUTING.md)检查、提交并同步 GitHub。调整周次时同步总路线与 README，保持只有一份权威周任务表。
